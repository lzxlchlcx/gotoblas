# 实验日志

## 2026-05-24 AVX2 DGEMM 优化 + 日志系统

### 1. 修复 AVX2 CPU 检测 Bug

**文件**: `src/kernel/avx2/cpuid.c`

**问题**: `__get_cpuid(7, ...)` 对 CPUID leaf 7 返回全零 EBX，导致 AVX2 永远检测不到，始终回退到标量 generic kernel。

**修改**: `__get_cpuid(7, &eax, &ebx, &ecx, &edx)` → `__get_cpuid_count(7, 0, &eax, &ebx, &ecx, &edx)`

**效果**: n=1024 单线程从 5.6 GFLOPS → 25.5 GFLOPS (4.5x)

---

### 2. MR=8×NR=6 微内核 + 配置驱动框架

**文件**: `src/config/haswell.h`, `src/kernel/avx2/dgemm_kernel.c`

**修改**:

- `haswell.h`: `GEMM_HASWELL_D_MR` 4→8, `GEMM_HASWELL_D_NR` 8→6
- `dgemm_kernel.c`: 完全重写，引入 `#include "config/haswell.h"`，通过 `#if MR == 8 && NR == 6` / `#elif MR == 4 && NR == 8` / `#else` 三条路径：
  - MR=8×NR=6: 12 累加器 + 2 A YMM 加载，15/16 寄存器
  - MR=4×NR=8: 保留原有实现
  - 通用 fallback: 4×4 子块循环
- scalar fallback 统一抽取为 `dgemm_kernel_scalar()` 静态函数

**效果**: n=2048 四线程从 78.7 GFLOPS → 103.8 GFLOPS (+32%)

### 3. 日志系统

**新增文件**: `src/util/myblas_log.h`, `src/util/myblas_log.c`

**修改文件**: `src/myblas.h`, `src/api/dgemm.c`, `src/driver/gemm_driver.c`, `Makefile`, `test/bench_compare.c`

**设计**:

- 编译宏 `MYBLAS_ENABLE_LOG` 控制，关闭时所有日志宏展开为 `(void)0`，零开销
- `Makefile` 添加 `LOG=1` 选项，自动追加 `-DMYBLAS_ENABLE_LOG`
- API 层 (`dgemm.c`): 记录每次 `my_dgemm` 的 (m,n,k)、总耗时、GFLOPS
- Driver 层 (`gemm_driver.c`): 分别记录 pack_a / pack_b / kernel 累积耗时和调用次数

**踩坑**:

2. `bench_compare.c` 需要显式调用 `myblas_log_print()` 才会输出
3. `make compare` 需要先 `make LOG=1 lib` 编译带日志的库

**验证**: `make LOG=1 lib && make compare` 输出包含调用次数、分阶段耗时、GFLOPS

## 2026-05-24 修复 OpenBLAS 线程控制

**文件**: `test/bench_compare.c`

**问题**: 原代码使用 `setenv("OPENBLAS_NUM_THREADS", ...)` 在运行时设置环境变量，但 OpenBLAS 在进程加载时（动态链接器 constructor 阶段）就已经初始化了线程数，运行时 `setenv` 不会生效。这导致 benchmark 中 OpenBLAS 实际使用了多核（n=2048 时达 611 GFLOPS，远超单核理论峰值 ~88 GFLOPS），性能对比数据不准确。

**修改**:
- 添加 `#include <openblas_config.h>`
- 将 `setenv("OPENBLAS_NUM_THREADS", ...)` 替换为 `openblas_set_num_threads(t)`，这是 OpenBLAS 官方运行时 API，调用后立即生效

**效果**: 使 OpenBLAS 线程数与 MyBLAS 保持一致，benchmark 数据准确反映同线程数下的真实性能差距

## 2026-05-25 reorder-gemm-driver-loops + Makefile 跨平台 OpenBLAS 路径

### 1. reorder-gemm-driver-loops（driver 循环重排）

**变更名**: `reorder-gemm-driver-loops`

**文件**: `src/driver/gemm_driver.c`, `openspec/changes/reorder-gemm-driver-loops/tasks.md`

**背景**:

- 原 driver 控制流中 `col1` 在 `row1` 外层，导致同一个 `(row1, k0)` 的 `MR x Q` A 微块在不同 `NR` 列块上被重复 `pack_a`
- 重复 packing 不改变结果，但会放大打包开销并拖慢大矩阵吞吐

**修改**:

- 双精度与单精度 driver 都改为：
  1) 在每个 `(col0, k0)` 内先打包当前 `R` 范围全部 `Q x NR` B 微块到 `sb`
  2) 再遍历 `row0/row1`，每个 `MR x Q` A 微块仅 `pack_a` 一次
  3) 在内层遍历 `col1` 复用该 packed A，调用多个 `NR` kernel
- 保持 kernel/pack 函数接口和 C 子块偏移语义不变，仍使用 `sb + k_rem * (col1 - col0)`

**验证**:

- 构建通过：`make`
- 正确性通过：`make test`，`20 passed, 0 failed`
- 已完成 OpenSpec tasks：`1.1~1.4`、`2.1~2.3`
- 性能 tasks `3.1~3.2` 需在“重排前/后”同机同参基线下继续补齐

### 2. Makefile 适配 macOS / WSL 的 OpenBLAS 路径

**文件**: `Makefile`

**问题**:

- `OPENBLAS_INC` / `OPENBLAS_LIB` 未设置时，`compare` 规则中的 `-I$(OPENBLAS_INC)`、`-L$(OPENBLAS_LIB)` 参数会错位
- 现象为 `clang: error: no such file or directory: 'test/bench_compare'`（实为参数解析错位，不是源码文件丢失）

**修改**:

- 新增平台检测：
  - `UNAME_S := $(shell uname -s)`
  - `IS_WSL := $(shell uname -r | grep -qi microsoft && echo 1 || echo 0)`
- 增加可覆盖的默认路径（`?=`）：
  - macOS (`Darwin`):
    - `OPENBLAS_INC=/opt/homebrew/opt/openblas/include`
    - `OPENBLAS_LIB=/opt/homebrew/opt/openblas/lib`
  - WSL:
    - `OPENBLAS_INC=/usr/include/x86_64-linux-gnu`
    - `OPENBLAS_LIB=/usr/lib/x86_64-linux-gnu`
- 保留命令行覆盖能力：
  - `make compare OPENBLAS_INC=... OPENBLAS_LIB=...`

**验证与注意事项**:

- 路径适配后，`make compare` 可正确生成 OpenBLAS 编译参数
- 若出现 `_myblas_log_print/_myblas_log_reset` 未定义，需要带日志库构建：
  - `make clean && make compare LOG=1`

## 2026-05-26 AVX2 DGEMM 8x6 kernel alpha live range 实验

**文件**: `src/kernel/avx2/dgemm_kernel.c`

**背景**:

- `MR=8, NR=6` fast path 主循环有 12 个 C accumulator、2 个 A vector、1 个 B broadcast，理论最小需求约 15 个 YMM。
- 原实现把 `valpha = _mm256_set1_pd(alpha)` 放在 `p` loop 前，虽然 `alpha` 只在 loop 后乘回 C accumulator，但编译器可能让 `valpha` 跨 loop 常驻 YMM。
- 如果 `valpha` 常驻主循环，寄存器需求会从 15 YMM 变成 16 YMM，完全占满 AVX2 的 16 个 YMM，后续调度或展开很容易触发 spill。

**尝试 1: 利用腾出的 YMM 预取下一个 B broadcast**

- 将 `valpha` 移到 `p` loop 后。
- 尝试在处理 `b0` 时提前生成 `b1`，形成短流水：同时保留 2 个 B broadcast。
- x86_64 AVX2 汇编检查结果显示主循环出现 YMM spill/reload：

```text
vmovapd %ymm13, 96(%rsp)   ## 32-byte Spill
...
vmovapd 96(%rsp), %ymm13   ## 32-byte Reload
```

**结论**: 即使移除了 `valpha` 的主循环 live range，同时保留 `12 accumulator + 2 A + 2 B` 仍会达到 16 个 YMM；编译器还需要额外 scratch/分配余量，因此实际触发 accumulator spill。该方向暂不采用。

**尝试 2: 保守缩短 alpha live range + 单 B broadcast 复用**

- 保留 `valpha` 移到 `p` loop 后的修改。
- 将 `b0..b5` 改为单个 `__m256d b` 逐列复用，明确缩短 B broadcast 生命周期。
- x86_64 AVX2 汇编检查结果：

```text
vmovupd       A0 -> ymm13
vmovupd       A1 -> ymm14
vbroadcastsd  B[j] -> ymm15
vfmadd231pd   ymm15, ymm13, accumulator
vfmadd231pd   ymm15, ymm14, accumulator
...
vbroadcastsd  alpha -> ymm13   # 出现在 p loop 后
```

- 主循环内未发现 `vmovapd/vmovupd` 对 `%rsp` 的 YMM spill/reload。

**验证**:

- 生成 x86_64 AVX2 汇编：
  - `clang -target x86_64-apple-darwin -O2 -Wall -Isrc -D__AVX2__ -mavx2 -mfma -S src/kernel/avx2/dgemm_kernel.c`
- 当前 macOS/arm 环境 `make test` 通过：`20 passed, 0 failed`。
- 注意：本机默认目标为 arm64，Makefile 的 AVX2 检测不会把 AVX2 object 编入库，因此 `make test` 只验证非 AVX2 路径未受影响；AVX2 路径需要在 x86_64/WSL 机器上继续 benchmark。

**当前结论**:

- 移动 `valpha` 到 loop 后是低风险优化，可以释放主循环寄存器压力。
- 用单个 `b` 变量复用 broadcast 比同时保留 `b0/b1` 更安全。
- “预取下一个 B broadcast”在 C intrinsics 层面容易让 YMM live set 顶满，除非手写汇编精确控制寄存器，否则暂不作为当前版本方案。
